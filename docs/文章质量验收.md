# 文章质量验收（T-008）

本文件记录 T-008 的数据流梳理、报告腔来源、改动、基准和验收方法。验收分两层：离线测试只证明“输入传到了哪里、导出没被破坏”，**不能代替文章质量验收**；文章是否真正变好，只能在用户授权调用模型后，用同一资料包做前后对照，再由人工评分判断。

## 1. 数据流（代码现状，2026-10-19 梳理）

| 阶段 | 输入 | 产出 | 代码位置 |
|---|---|---|---|
| 正文与摘要 | 公众号原文（微信读书正文或图片识别转写） | 每段 `analysis`：`summary`、`facts[{claim, quote}]`（quote 必须逐字出现在原文）、`uncertainties` | `api.py` `Model.summary`、`engine.py` `_summaries` |
| 风格分析 | 热度最高素材的原文前 24000 字 | `style_reference`：标题、开头、结构、语气、节奏、结尾六项，挂在第一篇素材上 | `api.py` `analyze_style`、`engine.py` `_style`（缓存键 `style-v2`） |
| 联网研究 | 第一篇素材的标题、`analysis`、评论关注点 | `web_research`（带 `[W数字]` 的研究笔记）和 W 来源，挂在第一篇素材上 | `research.py` `WebResearch.search` |
| 初稿 | `sources`（含 analysis、style_reference、web_research、指标）、`topic`、`style`、目标字数 | `title`、`outline`、带 `[S]/[W]` 标记的 `body`、`review_notes` | `api.py` `_write_once` |
| 二审 | 初稿 + `evidence`（来源编号、标题、analysis、web_research） | 修订后的完整稿件和 `quality_notes` | `api.py` `review` |
| 保存 | 稿件、来源列表和素材报告 | 稿件库正文**保留** `[S]/[W]` 标记；素材报告保留每篇原文的摘要、事实与原文证据、联网资料 | `engine.py` `_write_one`、`_report` |
| 导出 | 稿件库正文 | 删除 `[S]/[W]` 标记，文末附实际引用的网站列表 | `ui.py` `export_document` |

修改前二审**没有收到** `style_reference` 和用户 `style`，但提示要求它“保留参考稿的通用节奏”。

## 2. 报告腔来自哪里

基准《稿件-10.md》的小标题、段首标签和结尾说明，几乎逐词对应修改前写作和二审提示中的审稿用语：

| 稿件中的文字 | 修改前提示中的原句 |
|---|---|
| “核心变化与本文价值点” | 二审第 4 项：“开头在短篇幅内给出核心变化及读者价值” |
| “可核实的事实”“关于……的证据与局限”“证据边界” | 二审第 2 项：“将原文观点、已核实事实和编辑推断清楚区分，证据不足的内容删除或降格表达” |
| “可能解释（基于证据的合理推断）”“结语（编辑判断的范围说明）” | 写作提示：“事实、来源观点与编辑判断要明确区分”；“推断必须使用‘可能、预计、仍需观察’等边界词” |
| 结尾“（文中区分了可核实事实与经验性观察或推断，并在每一相关句后标注了现有证据来源。）” | 写作和二审都要求“关键事实使用 [S数字] 标记”“来源标记紧跟受支持的句子”，模型把这一要求写成了对读者的说明 |
| 全文 67% 的行是“- 标签：”式列表 | 摘要阶段的 `facts[{claim, quote}]` 结构，加上“每节回答一个具体问题” |

**已证实**：上表中的提示原句存在于修改前代码（Git `2c94c2a` 的 `wewriter/api.py`）；导出代码只删除标记、追加网站列表，没有任何后处理会把正文改成“事实/推断”分节（`ui.py` `export_document`）。

**推断，未证实**：报告结构出现在初稿还是二审阶段，无法确定。稿件库只保存终稿，没有保存当时的初稿、原文、研究笔记和模型配置，因此不能重现历史生成过程。二审缺少风格上下文时只能依赖审稿清单，这很可能加重了报告腔，需要用模型对照来验证。

**不是缺陷**：发布稿删除正文引用编号是有意设计，按用户 2026-10-19 指示保持不变；论述与来源的对应关系保留在稿件库正文和素材报告中。基准结尾声称“每一相关句后标注了来源”，与导出稿没有编号不一致，问题在于正文写了过程说明，而不在于删除编号。

## 3. 本轮改动（`wewriter/api.py`）

- 新增 `ARTICLE_VOICE`：事实与推断的区分体现在措辞上，不得按可信程度分节，不得把审稿用语用作小标题或标签；以段落叙述为主；正文不得描述写作、审核过程或来源标记。写作和二审都使用这段要求。
- 新增 `FACTS_FIRST`：事实准确与证据支持高于用户 style，用户 style 高于 style_reference；不得为了模仿风格编造经历、人物、场景、对话、数字、引语或情绪化细节。写作和二审都使用这段要求。
- 二审输入新增 `style_reference`（与初稿使用的同一对象，由 `style_context(sources)` 取得）和 `style`；审稿清单注明“各项是审稿标准，不是正文小标题”；第 4 项改为“说明这件事与读者的关系”，第 6 项改为对照 `style_reference` 和 `style` 保持一致，没有时保持初稿的组织方式。
- 来源校验不变：二审仍不能新增资料中没有的来源编号。未改导出、缓存键、调用次数（写作最多 2 次，即首次加一次格式修复；二审 1 次）、研究阶段和数据库。

### 第 2 轮离线修正（2026-10-19，依据揭盲后的问题和用户细化的三条规则）

- `FIDELITY_RULES`（写作与二审共用）：
  - style_reference 只提供表达方式，不提供事实。资料没有现场细节时，用已有事实、读者问题或明确标注的假设开篇，不把缺失场景补写成事实。
  - 加引号的直接引语必须能逐字核对。不加引号的转述可以概括，但不能改变含义、扩大受访者范围或强化程度和情绪。
  - 数量推断必须核对分母和口径：比例变化不等于人数变化；缺少基数不写绝对人数；有同口径数据时写明条件再推导。
- 二审在同一次调用中先返回内部 `claim_checks`（原句、对应证据、保留／修正／删除、说明），程序校验格式后转成“逐句核对｜…”写入素材报告的“AI 二审”部分，正文中不出现。缺少或格式无效时视为二审未完成，保留初稿并给出警告。调用次数不变。
- 程序核对引号：正文中 6 字以上的引号内容若在资料中找不到（忽略空白和标点），写入 review_notes 提醒人工核实，不自动改写正文。
- 新增 `tests/fixtures/article_quality/package_report_style.json`：重建的虚构资料包，用于单独检验报告腔（原文多为吐槽和传闻数字，联网资料包含日期明确的公告、口径不清的媒体数字和机构观点）。它**不是**《稿件-10》的历史输入，不能称为历史复现。
- 评估脚本 `--baseline-rev` 支持 `file:<api.py 快照>`。第 1 轮提示快照保存在 `.local-data\article-quality\prompts\api-t008-round1.py`（SHA-256 `89d4912c…6690`），它产生的系统提示哈希与第 1 轮 current 样本记录的 `prompt_sha256` 完全一致（已核对 3 个样本）。

### 第 3 轮离线诊断与修正（2026-10-20）

- 审计（`.local-data\article-quality\audit-round2.md`）：第 2 轮的否决错误大多在初稿中已经存在，但二审漏检或核对后仍保留；另有 4 处由二审新增。逐句核对完全没有覆盖标题；核对只证明“来源说了什么”，没有验证“被广泛传播”之类的断言。
- 修正：第四条忠实性规则覆盖标题、导语、传播范围、热度、时间、关注度、判断依据和来源定性。逐句核对要求先核对标题，并覆盖二审新增或改写的句子。程序提示传播类断言、标题未核对、未经核对的新增句，提示只写入审核备注，正文不受影响。表达上改用归属明确的说法，删去不影响主线又缺乏支持的内容，关键风险留在正文中说明。
- 篇幅：初稿已经偏短，二审没有压缩，也没有截断，目标字数已正确发送。原因主要是资料稀少，不建议强行扩写。
- 未调用模型，第 3 轮对照需另行授权。

## 5. 验收方法

### 5.1 离线（已执行，见 HANDOFF）

`.\.venv\Scripts\python.exe -m unittest discover -s tests -p 'test_article_quality.py' -v`：二审收到与初稿相同的 `style_reference` 和 `style`；两轮提示都包含事实优先和禁止报告结构的要求，旧审稿用语已移除；没有风格参考时保持初稿组织；二审新增来源会被拒绝；单篇流程中二审拿到的风格与写作一致；导出不含编号，内部对应关系保留；评估脚本的规则检查、资料包校验、空白评分表、哈希校验，以及未授权时拒绝付费调用。评估脚本复审修正后另覆盖：中性编号与密封映射、未评分时拒绝揭盲、提示常量改变时哈希随之改变、失败与审核提示脱敏、连续失败停止、致命错误停止、达到调用上限停止。

### 5.2 文章对照评审（需用户授权，尚未执行）

```powershell
.\.venv\Scripts\python.exe scripts\evaluate_article_quality.py generate --package tests\fixtures\article_quality\package.json --provider deepseek --runs 3 --baseline-rev 2c94c2a --allow-paid-calls
.\.venv\Scripts\python.exe scripts\evaluate_article_quality.py check --baseline .local-data\article-quality\baseline\稿件-10.md --baseline-sha256 77139e7b1d8bc973ed08545478d9e3a631e91a5d645bcd32d46303204fb07b01 --candidate <生成的稿件> ...
```

- 同一资料包、同一模型和完整有效配置（写入 `run.json`），分别用修改前（`2c94c2a`）和修改后的提示各运行 3 次，按随机顺序执行。
- 调用次数：正常情况每个样本 2 次模型请求（写作 1 次、二审 1 次），6 个样本共 12 次；写作格式校验失败时会多 1 次修复请求。硬上限按**实际 HTTP 请求**计算，包括 `Transport` 对 429/502/503 的自动重试，因为重试过的请求不能断言服务器没有处理或没有计费。每次请求发出前先检查预算，新旧两版提示使用同一预算。默认上限 18 次（6 个样本 × 3），可用 `--max-calls` 调低，必须是正整数；发生重试时会更早达到上限。按供应商计费。
- 停止规则：达到调用上限、遇到 Key 无效、余额不足或无权限等致命错误，或连续 2 个样本失败时，立即停止，不再继续调用。
- 追溯：每个样本记录本次实际发送的系统提示的哈希（`prompt_sha256`）和完整请求的哈希（`request_sha256`），提示常量改变时哈希随之改变；同时记录耗时和调用次数。失败样本保留，错误文本和审核提示都经过集中脱敏。
- 盲评：样本文件使用随机中性编号（`samples/sample-xxxxxx.md`），评分表只列编号；版本映射单独保存在 `sealed/blind-key.json`，评分前不要打开。所有样本都填完总分后，再运行 `evaluate_article_quality.py reveal --run <目录>` 揭盲；有样本未评分时脚本会拒绝揭盲。
- 人工评分（盲评，隐藏版本）：自然表达（无报告腔）20、叙事连贯 20、信息价值 20、风格匹配 15、事实与引用可靠 15、手机阅读 10。否决项：编造事实、数字或人物经历；伪造引语；来源不支持关键结论。建议门槛：修改后总分不低于 75，且比修改前高至少 20 分。
- 规则检查只作参考：报告腔小标题、过程说明、列表占比下降，并不代表文章变好。
