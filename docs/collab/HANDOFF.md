### 设计说明与判断（请重点审查）

- A：持久化边界放在 `Database.update_job`，所有任务写入都经过它；`articles.error` 改走 `set_article_error`。funnel 只脱敏 `accounts.*.error`、`coverage.reason`、`collection.warnings`。文章正文、稿件正文、素材报告和 `drafts.sources` 不做全局替换，测试证明正文中的示例 Bearer 原样保留。历史清理（v4 迁移）只处理 jobs.message/warnings/funnel 与 articles.error，不删除任务或正文；`redact` 幂等，重复启动结果不变。旧备份恢复时 `_stage_restore` 会执行迁移，因此同样清理。**未清理**：历史稿件素材报告中的评论失败原因或二审失败提示（属于稿件内容，按要求不改写）；新任务从写入前就脱敏。Cookie 规则会遮盖整段 Cookie 值，直到换行、引号或中文“；，。”，同一行其后的 ASCII 内容也会被遮盖，偏保守。

## 六项问题与具体验收

### A. 持久化诊断脱敏（最高优先级）

证据：虚构 Bearer 错误写入时，funnel 中已脱敏，jobs.warnings 中仍有原值。尚未发现真实凭据泄漏。

- 审计 warnings、message、文章 error、批量子任务诊断及 UI 通知路径，使用集中脱敏逻辑。不要仅修一个调用点；普通文章正文和用户稿件不能被全局替换破坏。
- 新持久化诊断与读取展示均应有安全边界。历史诊断若仍含凭据，必须说明处理范围；若实施一次性清理，只针对诊断字段、使用有序幂等迁移并测试，禁止删除任务/正文。备份路径不得重新带出未处理的历史诊断。
- 使用明确虚构 Bearer、API/Skill Key、Cookie、异常消息测试，断言数据库诊断字段、展示文本及测试备份不含原值，同时保留错误类型与请求 ID。不得读取任何真实凭据或真实数据库。

### B. 阅读量可信度

证据：用户同标题文章页面显示阅读 1068，软件显示 0。代码使用 mpInfo.readNum/likeNum，但没有原始响应证明差异原因。

- 先检查仓库内接口资料、适配器和已有模拟样例，列出可证实字段契约、来源与采集时间。不得把“页面另一条异步请求”或“0 是占位”当成已证实事实。
- 可信指标应有来源和观察时间；区分合法数值 0、字段缺失、无效或来源不可信。不能把所有 0 变未知，也不能将未知转 0 参与热点排名；未知数据应明确提示并说明选文影响。
- 如资料支持正确字段或更新路径，实施并用脱敏结构的虚构 fixtures 验证读取、持久化、显示和排名链路；保留其他来源已有非零数据时明确新旧指标替换规则，避免静默覆盖。
- 若必须取得真实响应才能确定契约，停止本项猜测，继续其余五项。交接列出需要用户自行提供的最小脱敏字段结构、对照截图和时间；不要求 Key/Cookie、原始请求头或完整账号响应。未证实差异原因时本项不得标记修复完成。

### C. 批量警告和质量结果

证据：采集阶段 collection_warning 在 run_separate 结束时被 failures 列表覆盖；父任务只按稿件数量判定完成，可能掩盖子任务联网降级。

- 按阶段保留采集警告、素材处理失败、子任务联网降级和质量警告，父任务详情能追溯对应公众号/子任务。
- 完成数量和质量提示分别表达。目标篇数达成但存在降级，界面仍需显著提示；不得声称所有稿件均完成联网研究。
- 重试仅替换本次更新阶段的结果，不重复累加警告，不抹掉仍然有效的采集覆盖说明。
- 覆盖采集告警+成功生成、子任务仅原文降级、局部失败补位、单篇重试刷新父任务、重复重试、多个阶段同时告警的回归测试。

### E. 继续任务与重新采集

## 剩余风险

- `os.replace` 在 Windows 同卷 NTFS 上使用 `MoveFileEx(REPLACE_EXISTING)`，实践中是原子的，但 Windows 文档没有正式保证原子性。
- 恢复时如果其他线程或进程持有正式库连接，`journal_mode=DELETE` 无法切换，或者 `os.replace` 会因文件被占用而失败。这两种情况都会拒绝恢复并保留原库，但用户需要先关闭任务后重试。UI 侧已有 `require_idle()`。
- `_swap_in` 的 checkpoint 与 replace 之间存在极短的窗口，期间若有新连接打开，替换可能失败（会被安全拒绝），不会造成半恢复。
- 如果进程在 `journal_mode=DELETE` 之后、替换之前崩溃，正式库会停留在 DELETE 模式，内容不变；下次启动时 `Database.__init__` 会重新设为 WAL。
- `verify_delivery.py` 会导入 `main` 和 `wewriter.ui`，因此需要可用的 Tkinter；无 GUI 的 CI 环境未验证。
- 启动失败时的弹窗只用 mock 测试过，没有在真实窗口中人工查看过（清单 C3）。
- 本轮没有修改 `REQUIREMENTS.md`/`PLAN.md`。
